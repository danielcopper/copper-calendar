## Decisions

- D2 (2026-11-09): The app reads only from Home Assistant and keeps the last result in a local cache; the widgets draw from that cache. Nextcloud stays the store for events and is never contacted by the app, and Home Assistant keeps the rules.

- D9 (2026-11-09): The app signs in with Home Assistant's own login (OAuth with PKCE), each person with their own account, and keeps the refresh token. It uses one address at home and away, the Nabu Casa URL; no switching between internal and external URLs.
- D10 (2026-11-09): No public page. The app's `client_id` is `http://127.0.0.1:<port>/` and its redirect `http://127.0.0.1:<port>/callback`; Home Assistant accepts a redirect on the same scheme and host as the `client_id` without fetching anything (`indieauth.py` at Core `2026.10.4`). The app listens on that port only during sign-in, uses PKCE, and keeps the exact `client_id` string, since a refresh needs the same one. Whether the login page redirects there in the phone's browser is checked on the first real sign-in; the fallback is a page in Home Assistant's `www` folder naming a custom-scheme redirect.
- D11 (2026-11-09): Each widget shows all calendars Home Assistant delivers; the setup app lets each widget leave calendars out. That is a view setting, not access control. Access control belongs to Home Assistant (planned later with Authentik and roles); the app shows whatever the signed-in account receives, so it needs no change when that comes.

- D26 (2026-11-10): The first test on a real phone (Pixel 10 Pro, Android 17, 2026-11-10) confirms D8 for the month widget: its drawn week rows scroll, a tap on the header, a day or "+" opens the Home Assistant app, light and dark switch with the system, and resizing redraws. Tap areas per entry are checked with the week widget.
- D27 (2026-11-10): Once the app fetches from Home Assistant (D3), a widget returns to today on each update, with today's row on top: the month's current week, the week's current day; an update is then each fetch and midnight. Until then the month only scrolls its current week into view. The setup app makes this a setting per widget, "Zurück zu heute": on each update (the default), only at midnight, never, or every 15, 30 or 60 minutes. Shorter intervals were dropped: WorkManager runs periodic work no more often than every 15 minutes, and shorter alarms are inexact and deferred while the phone dozes unless they are exact, which needs a permission the user grants by hand.
- D28 (2026-11-10): Gradle checks every dependency the build resolves, plugins included, against SHA-256 checksums in `gradle/verification-metadata.xml`, and locks the resolved versions of the app's configurations and of the build script's classpath in lock files; Robolectric's own download of its Android jars at test time is outside both; a dependency change rewrites both with `mise run deps-refresh`, and the diff is read before the commit. This answers SonarQube Cloud's findings that dependencies are neither verified nor locked; accepting them in SonarQube Cloud was the alternative and was dropped, since the checks cost one command per update. Checksums only, no PGP signatures: an update rewrites the lock files in any case, and signatures would add a key ring to keep and a key server to reach on each rewrite, while 55 artifacts would still need checksums, 33 of them unsigned (among them the ktlint plugin and the SonarQube plugin's marker) and 22 signed with one of six keys no key server had (2026-11-10).
- D29 (2026-11-10): Dependabot does not rewrite the checksums (it has no support for Gradle's verification metadata, dependabot-core issue 1996, open since 2020); of the lock files it rewrites only `gradle.lockfile`, by running Gradle, which then fails on the missing checksum, and `buildscript-gradle.lockfile`, where the plugins are locked, it never touches. So its Gradle pull requests stay red until a person runs `mise run deps-refresh` on the branch, reads the diff and pushes it; a CI check fails a pull request whose lock files or checksums no longer match what its dependencies resolve to and names that task. Checksums a removed dependency leaves behind do not fail it; `mise run deps-refresh` drops them. A workflow that rewrites both and commits them with a GitHub App's or a personal access token, so the checks run again on its commit, was the alternative and was dropped: for a repository with one maintainer it is a secret with write access to set up and keep, and new checksums would land without anyone reading them.
- D30 (2026-11-10): A tap on a Home Assistant target starts two things, one after the other: first the app that handles the link, started as its icon starts it (its launch intent from the package manager, `ACTION_MAIN` with `CATEGORY_LAUNCHER`), with `FLAG_ACTIVITY_NEW_TASK | FLAG_ACTIVITY_CLEAR_TASK`; then the link itself, without flags. Back from the target then returns to the page the Home Assistant app itself opens with. The app is found by the link's scheme, not by a package name, since Home Assistant ships more than one build (a full and a minimal one); this app declares that it looks for the apps that open `homeassistant://navigate` links (`<queries>`), which Android 11 and later require before they show another app. The query names the host too: Android matches a query against the other app's filters, a query without a host matches no filter that names one, and the Home Assistant app's filter names `navigate`; the first build of this variant had no host, saw no app and opened every link alone (2026-11-10). When no app is seen to handle the link, when several do and none is the default, or when the one that does has no launcher entry, the link opens alone in a new task, without clearing, and the log says which; with no app at all it then fails as before (D25). A target in another app opens alone, in a new task. Without this, each tap stacked one more calendar page in the Home Assistant app's task, so back stepped through every earlier tap: its `LinkActivity` (`singleTask`) starts a new `LaunchActivity` (standard launch mode, no flags) for every `homeassistant://navigate/…` link (read in home-assistant/android at `c6eb57c`). Two variants failed on the phone (2026-11-10). Clearing the task and opening the target alone left one page, but back closed the Home Assistant app. Opening the dashboard's start page link first and the target link after it worked from a shell, but from the widget the two links reached the system 4 to 7 ms apart, both to the same `singleTask` `LinkActivity`, and the system's log showed one `LinkActivity` displayed and one `LaunchActivity` started: `LinkActivity` ignores a further link it receives while it is still open. The launcher start goes to another activity than the link, so the link cannot land in an open `LinkActivity` that way. Measured on the phone (2026-11-10): started back to back with `adb`, the calendar opens on the tapped day, the task holds two `LaunchActivity` records, and back returns to the Home Assistant app's own start screen. From the widget, nine taps with the Home Assistant app running each started it as its icon does, with `FLAG_ACTIVITY_NEW_TASK | FLAG_ACTIVITY_CLEAR_TASK`, and then the link, with no fallback logged and no background start blocked; the task held exactly two `LaunchActivity` records, and back returned to the app's start page. With the app not running (swiped away), a tap works too and takes longer. The system lists the Home Assistant app among the apps this one may see (`dumpsys package queries`). The cost: whatever the user had open in the Home Assistant app is gone after a tap, and the app loads two pages per tap. The opening animation ran twice in the shell test of two page links; for the launcher start it was not looked at. Waiting for a fix in the Home Assistant app was dropped: issue home-assistant/android#5381 is open, and pull request #7163 covers only notification commands. Once that app opens navigate links in place, a tap goes back to opening its target alone, without clearing.
- D31 (2026-11-10): The app is called "Copper Calendar", in English, as a name that is not translated. The widgets are named in German: the month "Monat", and the two week widgets "Woche" (rows) and "Woche quer" (columns, D19). "Kalender" was dropped because it collides with Google Calendar's German name, and the widget picker groups widgets under the app's name; "Familienkalender" was rejected, and "Copper Kalender" mixes two languages. A name can change with any update; only the application ID is fixed once the app is on Play (D13).
- D32 (2026-11-10): The launcher icon is a calendar sheet with two binder rings and a grid of days, today marked, in one colour on a plain background: dark blue `#1E2B45` on light blue `#D8E2F7` in light mode, and light `#D8E2FF` on dark blue `#2B3245` in dark mode (night-mode resources). The days are the background colour at 45 % opacity, today at full colour. Its monochrome layer for themed icons is the sheet and its rings with the days cut out as holes: Android tints that layer and documents nothing about partial opacity in it, so the days are holes, not half-transparent. The sheet and the monochrome layer are vector drawables, the background a colour. Whether the launcher redraws the icon at once when the phone switches between light and dark is still to be checked on the phone. A house with a window grid, a "C" monogram and copper colours were the alternatives and were dropped.
- D33 (2026-11-10): The month widget's preview in the widget picker is a fixed image (`previewImage`): the widget as a launcher draws it from the sample month, in light mode, at its default size of 4 × 4 cells (276 × 456 dp) and xxhdpi. `mise run preview` renders it with the widget's own drawing and layout and writes it into the app's resources, and a test fails while the committed image differs from a fresh render, so a change to the drawing cannot leave an old preview behind. The drawing is the same on the dev machine and on CI as far as compared: the week rows, header and "+" drawn by main's CI run of 2026-11-10 and those drawn on the dev machine from the same commit are identical, pixel for pixel; the preview itself is first drawn on CI with the change that adds it. A new Robolectric or Android platform jar for the tests may change pixels; the check then fails until `mise run preview` has written the preview anew. `previewLayout` (Android 12 and later) was not used: it shows a layout from resources, and the widget's content is drawn at run time, so it would only frame this same image. A preview generated from the real data (`setWidgetPreview`, Android 15) can follow once the app has data.
